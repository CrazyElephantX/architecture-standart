# Задание 2: FURPS+ таблица требований

## Описание

Таблица архитектурно-значимых требований к MVP по цифровизации открытия депозитов в интернет-банке и на сайте банка. Требования собраны на основе анализа текущего процесса, IT-ландшафта компании и бизнес-целей.

## FURPS+ таблица требований

| Код | Требования | Комментарий |
|-----|-----------|-----------|
| **F** | **ФУНКЦИОНАЛЬНЫЕ (Functionality)** | |
| F.1 | Клиент может подать заявку на депозит через интернет-банк, указав счёт и сумму | MVP включает функцию подачи заявок только для существующих клиентов через интернет-банк |
| F.2 | Клиент может подать заявку на депозит через сайт, оставив контактные данные (телефон, ФИО) | Для новых клиентов, требует последующей идентификации в отделении |
| F.3 | Система отображает актуальные ставки по депозитам для клиента в интернет-банке | Ставки должны обновляться ежедневно, учитывая кредитный риск банка |
| F.4 | Система отображает персонализированные ставки для авторизованного клиента в интернет-банке | Ставки зависят от профиля клиента и его истории; персональные ставки отличаются от базовых |
| F.5 | Система отправляет СМС-уведомление клиенту о подтверждении ставки и открытии депозита | Требует доработки функционала СМС в ядре системы АБС |
| F.6 | Подтверждение операции открытия депозита в интернет-банке выполняется через СМС-код | Интеграция с существующим функционалом СМС в ядре АБС |
| F.7 | Менеджер бэк-офиса может просмотреть и обработать заявку на открытие депозита в АБС | MVP предполагает ручное подтверждение условий менеджером на этапе начальной реализации |
| F.8 | Система поддерживает ручное согласование ставок менеджером бэк-офиса перед открытием депозита | На MVP уровне это асинхронный процесс; в будущем может быть автоматизирован |
| F.9 | Система передаёт заявки с сайта в систему кол-центра для обработки | Новые клиенты требуют звонка от менеджера кол-центра перед идентификацией |
| F.10 | Сотрудник кол-центра может предложить клиенту специальные условия на основе заявки | Бизнес-функционал, зависит от профиля клиента и доступного бюджета |
| F.11 | Сотрудник кол-центра может просмотреть актуальные ставки по депозитам при консультировании | Необходимо предоставить доступ к системе управления ставками для кол-центра |
| F.12 | Система управления ставками доступна сотрудникам бэк-офиса (депозиты и кредиты) | Система должна заменить Excel-файлы как единый источник истины для ставок |
| F.13 | Ставки по депозитам обновляются ежедневно на основе данных о кредитном риске и ставке рефинансирования | Процесс обновления должен быть автоматизирован или полуавтоматизирован |
| **U** | **УДОБСТВО ИСПОЛЬЗОВАНИЯ (Usability)** | |
| U.1 | Интерфейс интернет-банка соответствует единой системе дизайна компании | Клиент должен видеть знакомые цвета, компоненты и брендированные элементы |
| U.2 | Процесс открытия депозита в интернет-банке занимает минимум действий (не более 5 шагов) | Клиент должен быстро завершить заявку без перегрузки информацией |
| U.3 | Процесс открытия депозита на сайте интуитивен для новых клиентов без технического опыта | Система должна быть доступна пожилым пользователям |
| U.4 | Интерфейс управления ставками в АБС удобен для сотрудников бэк-офиса и кол-центра | Должны быть быстрые поиск, фильтрация и редактирование ставок |
| U.5 | Обработка заявки менеджером бэк-офиса занимает не более 5 минут | Включает просмотр заявки, согласование ставки, создание депозита в АБС |
| **R** | **НАДЁЖНОСТЬ (Reliability)** | |
| R.1 | Интернет-банк должен быть доступен 24/7 с гарантией 99.9% uptime | Требование бизнеса для всех критичных сервисов |
| R.2 | Система должна обеспечить отказоустойчивость при сбое основного ЦОД | Банк имеет резервный ЦОД; необходимо предусмотреть переключение и горизонтальное масштабирование |
| R.3 | Потеря данных заявок на открытие депозита исключена (99.99% надёжность хранения) | Критичные данные должны реплицироваться между ЦОД |
| R.4 | Система должна восстанавливаться после сбоя в течение 15 минут (RTO) | После восстановления потеря данных за последние 5 минут допустима (RPO) |
| R.5 | Все критичные операции (открытие депозита, отправка СМС) логируются с полной аудитоустойчивостью | Требование регуляторов банка; необходимо восстанавливать последовательность событий |
| R.6 | Система управления ставками должна быть доступна сотрудникам кол-центра при частичном отказе АБС | Ставки кэшируются локально или хранятся отдельно для обеспечения консультирования |
| **P** | **ПРОИЗВОДИТЕЛЬНОСТЬ (Performance)** | |
| P.1 | Отклик на все операции в интернет-банке должен быть ≤ 500ms (95-й перцентиль) | Бизнес жалуется на задержки > 1 сек при загрузке справочных данных; необходимо оптимизировать |
| P.2 | Загрузка списка доступных депозитов с ставками в интернет-банке ≤ 200ms | Часто используемая операция; кэширование и индексирование обязательны |
| P.3 | Согласование и создание депозита в АБС должно происходить за ≤ 1000ms | Менеджер ждёт подтверждения; задержка влияет на опыт клиента в отделении |
| P.4 | Система управления ставками должна выдержать одновременно 100+ пользователей без деградации | Кол-центр может иметь много одновременных консультантов |
| P.5 | Система должна обрабатывать пиковую нагрузку 500 заявок в час без очереди > 10 сек | Маркетинговая кампания может резко увеличить количество заявок |
| P.6 | Интернет-банк должен равномерно распределять запросы между серверами в одном ЦОД и между ЦОД | Горизонтальное масштабирование; балансировщик нагрузки |
| P.7 | API между интернет-банком и системой управления ставками должен выдержать ≤ 100ms latency | Минимизировать сетевые задержки; рассмотреть кэширование в CDN |
| **S** | **ПОДДЕРЖИВАЕМОСТЬ (Supportability)** | |
| S.1 | Все системы должны быть документированы с описанием API, компонентов и процессов интеграции | Необходимо для масштабирования и добавления новых продуктов в будущем |
| S.2 | Код должен следовать стандартам компании и быть понятным для разработчиков (review-friendly) | Возможность быстрого онбординга новых разработчиков |
| S.3 | Логирование и мониторинг должны позволять отследить заявку от подачи до открытия депозита | Помощь при отладке и анализе инцидентов |
| S.4 | Система должна поддерживать расширение на новые каналы (мобильное приложение, USSD, Яндекс.Касса) | Архитектура должна быть модульной и слабо связанной |
| S.5 | Разработка и развёртывание новых функций должно быть возможно без влияния на существующий процесс открытия депозитов | CI/CD, feature flags |
| S.6 | Система должна быть совместима с существующими базами данных (MS SQL, Oracle) | Минимизировать введение новых технологий; использовать то, что есть в компании |
| S.7 | Выбранные технологии должны иметь экспертизу в компании или быть стандартами индустрии | Избегать редких языков/фреймворков, которые сложно поддерживать |
| **+R** | **+ ОГРАНИЧЕНИЯ (Restrictions)** | |
| +R.1 | Передача чувствительных данных (номер счёта, сумма, контакты) между сайтом и системой должна быть зашифрована (TLS 1.2+) | Требование PCI-DSS и банковских стандартов безопасности |
| +R.2 | Данные клиента из интернет-банка и сайта не должны передаваться напрямую в АБС | АБС перегружена; необходимо буферизировать через промежуточную систему или очередь |
| +R.3 | Интеграция с Kafka на горизонте > 6 месяцев; на MVP текущая версия интернет-банка несовместима | Рассмотреть асинхронную обработку через новый микросервис |
| +R.4 | Разделение доступа между сотрудниками кредитов и депозитов должно сохраняться по требованиям безопасности | Система управления ставками должна иметь RBAC для контроля доступа к данным |
| +R.5 | На MVP не требуется полная микросервисная архитектура интернет-банка, только для функции открытия депозитов | Возможна реализация как отдельный микросервис с API к интернет-банку |
| +R.6 | Отсутствие возможности прямого API вызова к АБС для интернет-банка; использовать очередь или синхронную очередь | Снижение нагрузки на АБС; асинхронная обработка заявок |
| +R.7 | Все системы должны быть готовы к миграции на микросервисную архитектуру в будущем | Использовать domain-driven design, event-driven patterns |
| +R.8 | Хранение и передача ставок между банком и партнёрским кол-центром должна быть через файлы (SFTP) | Партнёр не имеет возможности вызывать API; необходимо разработать процесс синхронизации файлов |
| +R.9 | Система должна поддерживать только русскоязычный интерфейс на MVP | Интернационализация может быть добавлена в будущих версиях |


## Дополнительные архитектурно-значимые требования

### Интеграционные требования

| Код | Требование | Комментарий |
|-----|-----------|-----------|
| INT.1 | Система управления ставками должна быть единым источником истины (Single Source of Truth) | Замена Excel-файлов; синхронизация с АБС, кол-центром и партнёрским кол-центром |
| INT.2 | Заявки из интернет-банка и сайта должны поступать в АБС для обработки менеджером | Асинхронная интеграция через очередь или синхронизацию по расписанию |
| INT.3 | СМС-уведомления должны отправляться через существующий функционал в ядре АБС | Минимизировать новые интеграции; использовать то, что уже есть |
| INT.4 | Система должна синхронизировать ставки с партнёрским кол-центром через SFTP ежедневно | Файловый обмен; возможность ручного управления при сбоях |

### Требования масштабируемости

| Код | Требование | Комментарий |
|-----|-----------|-----------|
| SCALE.1 | Интернет-банк должен масштабироваться горизонтально (добавление новых серверов) | Stateless приложение; load balancing между ЦОД |
| SCALE.2 | Система управления ставками должна масштабироваться горизонтально |  использовать кэширование и репликацию |
| SCALE.3 | АБС может масштабироваться только вертикально; буферизировать нагрузку перед ней | Не отправлять все запросы напрямую в АБС; использовать очередь |

### Требования к миграции и модернизации

| Код | Требование | Комментарий |
|-----|-----------|-----------|
| MIGRATE.1 | Архитектура должна позволять переход интернет-банка на микросервисы в будущем | Разработать API отделения функционала открытия депозитов |
| MIGRATE.2 | Система должна поддерживать интеграцию с Kafka без переработки основного кода | На перспективу; использовать event-driven patterns |
