## <a name="_3bfxc9a45514"></a>**Функциональные требования**


Описание верхнеуровневых Use Cases для MVP открытия депозитов онлайн.

| № | Действующие лица или системы | Use Case | Описание |
| :-: | :- | :- | :- |
| UC.1 | Клиент (интернет-банк) | Подать заявку на депозит | Авторизованный клиент переходит в интернет-банк, выбирает депозит, указывает счёт и сумму, подтверждает СМС-кодом. Заявка отправляется в очередь для обработки бэк-офисом. |
| UC.2 | Клиент (сайт) | Подать заявку на депозит | Новый клиент переходит на сайт, выбирает депозит, оставляет контакты (телефон, ФИО). Заявка отправляется в систему кол-центра для звонка менеджера. |
| UC.3 | Клиент (интернет-банк) | Просмотреть доступные ставки | Клиент видит список доступных депозитов с актуальными базовыми ставками и персональными ставками (если применимо). |
| UC.4 | Менеджер кол-центра | Консультирование по депозитам | Менеджер может просмотреть ставки, информацию о заявке и предложить клиенту условия при звонке. |
| UC.5 | Менеджер бэк-офиса | Обработка заявки | Менеджер просматривает заявку в АБС, согласует ставку (если нужна специальная), подтверждает условия и открывает депозит. |
| UC.6 | Система управления ставками | Синхронизация ставок | Каждый день система получает данные о кредитном риске и ставке рефинансирования, пересчитывает ставки и обновляет их во всех системах. |
| UC.7 | Партнёрский кол-центр | Получение ставок | Система ежедневно отправляет актуальные ставки партнёру через SFTP для консультирования их сотрудников. |
| UC.8 | Система управления ставками | Передача ставок в кол-центр | Сотрудники кол-центра имеют доступ к системе управления ставками для консультирования клиентов. |

### <a name="_qmphm5d6rvi3"></a>**Решение**

#### Концепция архитектуры

Архитектура MVP базируется на следующих принципах:

1. **Асинхронная обработка заявок** — избегаем перегрузки АБС через введение очереди между интернет-банком и АБС
2. **Единый источник ставок** — система управления ставками заменяет Excel-файлы и становится единой точкой доступа для всех систем
3. **Разделение ответственности** — каждая система имеет чёткие границы и отвечает за свою часть процесса
4. **Подготовка к микросервисам** — компоненты разработаны так, чтобы в будущем можно было развернуть их как отдельные микросервисы
5. **Минимизация новых технологий** — использование существующих в банке платформ (MS SQL, Oracle, Java/.NET)
6. **Безопасность по умолчанию** — TLS для всех каналов, RBAC, аудит всех операций

1. Java является отраслевым стандартом для fintech/enterprise решений де-факто по причинам LTS и безопасности
2. Развертывание новой службы отдельно от устоявшегося АБС монолита минимизирует стоимость разработки и внедрения
3. Независимый микро фронтенд развяжет руки для UI команды депозитов по числу и количеству релизов
4. Интеграция системы депозитов через event sourcing минимизирует сцепленность сервисов (decoupling), без потери интеграции
5. Выделение микросервисной архитектуры создает задел для постепенного отказа от ресурсоемокой ABS системы по методу Strangler Fig


#### <a name="_bjrr7veeh80c"></a>**Альтернативы**

##### Альтернатива 1: Синхронная обработка (без очереди)
**Описание**: Интернет-банк напрямую вызывает API АБС для создания депозита.

**Преимущества**:
- Простая реализация
- Немедленное подтверждение клиенту

**Недостатки**:
- АБС перегружена; может быть bottleneck
- Задержка интернет-банка при медленном ответе АБС
- Нарушает требование +R.2 и +R.6
- Невозможно масштабировать при пиковых нагрузках
- **Отклонено**

##### Альтернатива 2: Каждая система хранит свою копию ставок

**Описание**: Интернет-банк, кол-центр и АБС хранят собственные копии ставок, синхронизируемые ежедневно.

**Преимущества**:
- Децентрализованное хранилище
- Быстрый доступ к локальным данным

**Недостатки**:
- Нарушает требование INT.1 (Single Source of Truth)
- Риск несогласованности данных
- Сложная синхронизация при ошибках
- Сложная RBAC (разные версии в разных системах)
- **Отклонено**


##### Альтернатива 3: Event-driven архитектура с Kafka

**Описание**: Использование Kafka для асинхронной обработки событий вместо очереди.

**Преимущества**:
- Современный подход
- Scalability для будущих интеграций
- Event sourcing для аудита

**Недостатки**:
- Текущая версия интернет-банка несовместима с Kafka (требование +R.3)
- Требует миграции инфраструктуры (не в MVP)
- Сложнее в поддержке (новая технология)
- **Отложено на будущее (после 6 месяцев)**

##### Альтернатива 4: SFTP для всех интеграций

**Описание**: Использование SFTP для всех интеграций (интернет-банк → АБС, ставки → все системы).

**Преимущества**:
- Стандартный протокол
- Простая интеграция с партнёром

**Недостатки**:
- Асинхронность создаёт задержку для клиента
- Сложная обработка ошибок
- Нет real-time уведомлений
- Не подходит для интерфейсов пользователя
- **Отклонено** (используется только для партнёра)

#### **Недостатки, ограничения, риски**

##### Недостатки

1. **Асинхронность заявок**
   - Клиент в интернет-банке не видит немедленное подтверждение открытия депозита
   - Требуется отправить СМС-уведомление (может быть задержка на несколько секунд)
   - **решение**: Пользователь видит "Заявка принята на обработку" сразу же
2. **Ручное согласование менеджером на MVP**
   - На этапе MVP нет автоматизации согласования ставок
   - Требуется участие человека для каждой заявки
   - **решение**: Процесс может быть автоматизирован в следующих версиях
3. **Раздельное хранилище для заявок**
   - Заявки из сайта хранятся в системе кол-центра
   - Заявки из интернет-банка обрабатываются через АБС
   - **решение**: На будущее планируется единое хранилище заявок

##### Ограничения
1. **Интернет-банк не готов к Kafka** (требование +R.3)
   - Текущая версия построена как монолит
   - Требуется миграция на микросервисы для использования Kafka
   - **Временный обход**: Используется встроенная очередь
2. **АБС масштабируется только вертикально**
   - Нельзя добавить новые серверы АБС
   - Может стать бутылочным горлом при резком росте нагрузки
   - **решение**: Очередь буферизирует запросы; горизонтальное масштабирование других компонентов
3. **База данных АБС уже перегружена**
   - Добавление новых таблиц может ухудшить производительность
   - **решение**: Минимальное количество операций с БД АБС; использование кэша
4. **Отсутствие API между интернет-банком и АБС**
   - Требование +R.6 исключает прямой вызов API
   - Затрудняет синхронное взаимодействие
   - **Решение**: Используется очередь как промежуточный слой

##### Риски

| Риск | Вероятность | Влияние | Снижение |
|------|-------------|--------|----------|
| **Перегрузка очереди при резком скачке заявок** | Средняя | Высокое | Автомасштабирование consumer'ов; мониторинг размера очереди |
| **Сбой партнёрского кол-центра при получении ставок (SFTP)** | Низкая | Среднее | Ежедневный экспорт + бэкап; алерты при ошибках |
| **Несогласованность ставок между системами** | Низкая | Высокое | Single Source of Truth; кэширование с TTL; логирование изменений |
| **Задержка в отправке СМС-уведомления** | Средняя | Среднее | Retry mechanism; timeout 5 минут |
| **Отказ основного ЦОД** | Очень низкая | Критичное | репликации в резервный ЦОД; автоматическое переключение |
| **Нарушение безопасности при передаче данных** | Низкая | Критичное | TLS 1.2+; шифрование чувствительных данных; PCI-DSS compliance |
| **Ошибка в расчёте ставок** | Низкая | Критичное | Unit тесты; интеграционные тесты; аудит всех изменений |
| **Утечка информации через логи** | Низкая | Высокое | Маскирование персональных данных в логах; RBAC на доступ к логам |
